**BIP85 outputs (v1.29.0):** `bip85App` makes the BIP85 applications other than seed words, from the same 64 bytes (`bip85Entropy`: HMAC-SHA512 keyed "bip-entropy-from-k" over the key at `m/83696968'/app'/...`, every step hardened). WIF (app 2): the first 32 bytes, compressed, mainnet. XPRV (app 32): BIP85 puts the chain code first and the key second, the reverse of BIP32, with depth, parent fingerprint and child number 0. HEX (128169), Base64 (707764) and Base85 (707785, RFC 1924 alphabet) passwords take the length as a path number and slice the output. Dice (89101) read a SHAKE256 stream of the entropy (`shake256Reader`, a plain Keccak-f[1600] on BigInt lanes), take ceil(log2(sides)) top bits per roll and skip values at or above the number of sides; sides are limited to 2^31 - 1 because they are a hardened path number. Check the byte order of the XPRV, the padding byte (0x1f is SHAKE, 0x06 would be SHA3) and the rate (136 bytes for SHAKE256). Every application is a self-test vector from the BIP, and the tests compare all of them with @scure/bip32 and Node's SHAKE256.

**Reforge (v1.28.0):** the words search runs in two steps. `reforgePlan` picks one fixed plan from what was typed (fill 1-2 `?` words; all words typed: the phrase, every swap of two different words, every single word replaced; one word short: the missing word at every place, with the n duplicate phrases skipped) and `reforgeChecksumOk` keeps exactly the phrases with a valid BIP39 checksum. Then each one is stretched with the typed passphrase (`mnemonicToSeed`) and compared by `reforgeMatch` with the check value: a master fingerprint (32 bits, so matches are reported with their coincidence odds and the search never stops early), an address (receive 0 to 9 of account 0; the address's own bech32/bech32m or Base58Check checksum is verified first, so a typo is refused instead of wasting a long search), or an account xpub/ypub/zpub/tpub/upub/vpub at depth 3 (compares the chain code after the hardened path, then the public key). Address and key matches end the search. Things to check: that no plan can drop a candidate (the tests compare every plan with an independent enumeration and @scure's `validateMnemonic`), that `reforgeMatch` derives the documented paths, that "FOUND" is only said for a real match, and that a stopped search is never reported as complete. The passphrase search (`reforgePassCandidates`, `reforgePassSearch`) tries no passphrase first, then each line, ordered pairs and triples of different lines (joined with nothing or a space), in typed/lower/UPPER/Capitalised form (and trimmed), and with the box ticked one typo per guess (a character left out, doubled, swapped with the next, or in the other case); lines are kept exactly, and more than 1,000,000 guesses are refused before starting. Runs on the page's main thread in chunks (`reforgeYield`, MessageChannel so a background tab is not throttled), because the Content-Security-Policy rightly blocks workers. `ckdPriv` takes an optional precomputed parent public key, used only for non-hardened steps.

**Restore drill (v1.27.0):** `drillStart`, `drillCheck` and `drillEnd` compare what you type with the words and passphrase held for the current seed (`watchCtx`, the same copy the watch-only box uses). The words are hidden by CSS only (`body.drill-on`): they stay in the page, so it protects against looking, not against anyone who can read the page. The page reports positions, never the right words, and compares the passphrase after Unicode normalization (NFKD), like the seed derivation. The drill ends whenever the result changes (`setResult` calls `drillEnd`), which also wipes what you typed. It uses no storage and no network.

**Check your download (v1.27.3):** `dlCheck`, `dlCid`, `dlParse`, `dlPick`, `dlClear` hash the chosen file with the browser's own SHA-256 and compute a CIDv1 (raw, sha2-256, multibase prefix bytes `[1,0x55,0x12,0x20]`), then compare both against whatever the user pastes (a bare hash, upper case, a full `SHA256SUMS` line, a CID, or several values together; every value present must match for a MATCH verdict). The chosen file is read with `FileReader` only, never uploaded, stored or sent. `dlCid`'s length check (`w.length === 59`) matters: a loosened check would accept a truncated CID as real, so there is a dedicated regression test pasting a truncated CID and asserting it reports `none`, not a false match. Know the limit: a tampered copy of the page could lie about its own hash, which is why the page itself says to also check with `sha256sum` or the build attestation.

**Support this project / Bitcoin dictionary (v1.27.3):** `drawSupportQr`, `copySupport`, `buildDict`, `dictFilter` are both display-only with no secret-adjacent data; nothing here reads the seed or sends anything over the network (the Lightning QR is drawn from a fixed, published text value; the dictionary is a static array filtered client-side). Worth checking only for the honesty of the claims made in the UI text, and that the BIP/SLIP-coverage test (`tests/test.js`) still fails if the page names a standard the dictionary lacks an entry for.

**Stale-result guard (v1.26.1):** `inputSig`, `staleCheck` and `seedSig` record the inputs (rolls, word count, mode, both passphrases) at the moment of FORGE. If any of them changes afterwards, the words, fingerprint, address and watch-only data are cleared, so what is on screen (and what DOWNLOAD saves) always belongs to the inputs that made it. A Word draw seed depends on the passphrase only. The saved file uses the rolls remembered from FORGE, not whatever is in the box now. **Run counter (v1.29.1):** `forgeRun` moves on at every FORGE (`finishSeed`), every clearing by `staleCheck` and every `wipeSeed` (CLEAR ALL). `finishSeed` checks it after each `await` (fingerprint, first address, address list, watch-only data) and stops if it has moved, so an older run that is still working out its fingerprint and addresses can never write them back after you changed an input or cleared the page.

Tests worth reading too: `tests/oracle.test.mjs` compares the seed math with `@scure` on random inputs, and `tests/mutation.test.mjs` shows which deliberate breaks the in-page self-test catches and which only the CI probe catches.

Independent checks anyone can run: compare with SeedSigner's `tools/mnemonic.py`, or Ian Coleman's BIP39 tool run offline ("Base 10"/"Hex" mode for dice, "Binary" for coin flips).

Known limits: the randomness meter only catches lazy input; the curve code is not constant-time; coin-mode test vectors come from an independent implementation of SeedSigner's method (SeedSigner publishes none); Coldcard is untested; tested in Chromium but not Firefox or Safari.

## Outside reviewers wanted

VOIDFORGE has **not been independently audited**. If you can read JavaScript or know Bitcoin key handling, please look at the table above and open an issue with what you find, even if it is only "I read X and it looks right". A review of the seed math (wordlist, roll to mnemonic, checksum) is the most valuable. Findings that disagree with the in-page self-test are the most useful of all. Say which version and file hash you read (see the README) so others can tell what was reviewed.

## Asking for a review (copy and adapt)

> Hi, I wrote VOIDFORGE, a single-file offline dice/coin to BIP39 seed generator (github.com/Random21m/voidforge). It is meant to be read, not trusted. Could you spend about an hour on REVIEW.md's table? Priorities: (1) is the wordlist exactly the official one, (2) does anything besides SHA256 of the typed rolls influence the seed, (3) is there any way the seed or passphrase leaves the page. I would also welcome a second opinion on whether it is worth publishing at all. I will credit you in the changelog if you want, and I will not describe it as audited unless you say I may.

## Note on the fingerprint picture (LifeHash)

The picture is LifeHash version 2 of SHA-256 of the 4 raw fingerprint bytes, which is what Sparrow Wallet shows. It was checked against the real Sparrow picture for fingerprint `4fbf7566` pixel for pixel (fixture in `tests/fixtures/`), and by eye against Sparrow for three more wallets covering the other gradient families. It matches the `lifehash` npm package on every fingerprint tested. Two other LifeHash ports I tried disagree with it on some fingerprints (a PyPI package on some triadic gradients; an npm `@bcts/lifehash` beta on a few pixels in about 1% of cases); since the picture only has to match Sparrow's and the results above match, those ports were treated as outliers. The picture is display only and never affects keys or addresses; the 8-character fingerprint is the real check.
